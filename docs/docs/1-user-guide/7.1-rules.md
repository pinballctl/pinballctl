# Rules

Rules is the heart of Pinball CTL.

This is where gameplay behaviour is authored and orchestrated end-to-end: events are captured, then dispatched into actions across the machine.

In practice, Rules is one of the most important modules in the platform. It is the layer that turns raw machine inputs into intentional game flow, feedback, scoring, and control.

## What This Feature Does

Rules define what should happen when specific events occur.

At a high level:

- Triggers decide when a rule is considered.
- Conditions decide whether a matching trigger is allowed to continue.
- Actions define what happens when triggers and conditions pass.

## Validation Rules You Should Know

The editor flags missing essentials before save/sync.

Common trigger validation errors:

- no trigger groups
- empty group items
- missing hardware device/event
- missing system event
- missing custom event name

Common action validation errors:

- missing action type
- missing action target (event/flag/counter/device/scene)
- invalid counter name format
- missing counter value/delta where required
- invalid lighting start frame/tag values

## Practical Setup Examples

### Example 1: Start game on button click

Goal: clicking Start should emit a custom start request event.

Suggested setup:

- Trigger: Hardware -> Start button -> `CLICKED`
- Conditions: none
- Action: `Emit Event` -> `Custom` -> `START_GAME_REQUESTED`

### Example 2: Award bonus only if game is active

Goal: a lane switch hit increases bonus only during active ball play.

Suggested setup:

- Trigger: Hardware -> Lane switch -> `CLOSED`
- Conditions:
  - Flag `GAME_ACTIVE == True`
  - Flag `BALL_IN_PLAY == True`
- Action: `Increment Counter` -> `BONUS` delta `1`

### Example 3: Hold-to-repeat action with safety gate

Goal: repeatedly fire an action while button is held, but only if enabled.

Suggested setup:

- Trigger: Hardware -> Action button -> `REPEAT_WHILE_HELD` with `repeatMs`
- Condition: Flag `ENABLED == True`
- Action: `Pulse` selected output with controlled duration

### Example 4: Lighting scene at a tagged moment

Goal: start a scene from a named point and keep it paused until another rule continues it.

Suggested setup:

- Trigger: System -> Modes -> `MODE_STARTED`
- Action: `Apply Lighting Scene`
  - Scene: `mode_intro`
  - Start mode: `Load paused`
  - Start at: `Tag`
  - Tag: `intro_start`

### Example 5: Fault response rule

Goal: when fault is raised, immediately force warning output state.

Suggested setup:

- Trigger: System -> Faults / Safety -> `FAULT_RAISED`
- Conditions: none
- Action: `Set Output` -> warning output -> `HIGH`

## Authoring Tips

- Keep rule names explicit and short.
- Use tags for mode grouping and quick filtering.
- Prefer system events for lifecycle transitions and hardware events for player input.
- Use condition groups to keep complex logic readable.
- Validate in Preview before syncing to hardware.

## Execution on the Pi and ESP

The Pi evaluates conditions and maintains flags, counters, event timing and grouped trigger history. Rules with these checks, state actions, or Pi actions (audio, media, lighting scenes and custom events) run through the Pi. After conditions pass, any hardware actions go back to the ESP over framed JSON. Simple hardware-only rules without conditions or multi-input ALL matching run locally on the ESP for the fastest response. A mixed rule is owned by the Pi as a whole; its hardware actions are not also run locally.

Update both the Pi software and ESP firmware from this change before testing conditional hardware rules. Older firmware did not enforce conditions. Saving a rule in the editor is not evidence that older firmware can execute it correctly. Sync refuses Pi-owned rules when the connected firmware does not advertise rules runtime version 2. Sync the rules after updating, and re-arm only after configuration and safety checks succeed.

### Conditions and state actions

- **Flags:** compare true/false. Unset flags start false. Set Flag writes a logical rule flag; setting `ENABLED` does not arm coils or bypass ESP safety.
- **Counters:** Set Counter replaces the integer value; Increment Counter adds its delta (negative deltas subtract). Unset counters start at zero. Values are signed 32-bit integers; increments saturate at the bounds rather than wrap. All six comparison operators are supported.
- **Time Since Event:** compare elapsed milliseconds since the previous occurrence of the named event. A never-observed event does not satisfy the condition, even for a less-than comparison. When checking the current event name, this means the previous occurrence, not zero elapsed time.
- **Device State:** compare against an observed input/output/coil state supplied by the ESP. Unknown state does not satisfy a condition, including `INACTIVE`. Firmware observations cover up to 32 distinct condition devices (mapped identifiers up to 128 characters). Input state is debounced; coil state comes from the safety controller. State reflects the observation captured with the event, not a guarantee that hardware cannot change afterwards.

Conditions support ALL/ANY within each group and ALL/ANY across groups. Empty condition groups add no restriction. Unsupported conditions or invalid operators fail closed. A rule with unsupported actions or invalid state-action values is skipped and logged rather than partially firing hardware.

Rule counters and flags are shared by web workers and the bridge through transactional per-instance storage in `rules/runtime.sqlite3`. They persist across process/machine restarts. Reset game-specific counters explicitly with Set Counter (for example, a GAME_STARTED rule setting bumper hits to zero). Rule reloads preserve values; trigger history is tied to the rule definition. BOOT_COMPLETED clears gesture/timing/device history. These counters are logical rule values, not an automatic credit accounting or player-management service.

Observed GAME_STARTED/GAME_ENDED, BALL_STARTED/BALL_ENDED, ENABLE_GRANTED/ENABLE_REVOKED, HAS_CREDIT_TRUE/HAS_CREDIT_FALSE and IDLE_ENTERED/IDLE_EXITED events update their corresponding built-in flags. CREDITS_CHANGED (`credits`), BALL_STARTED (`ball`) and PLAYER_ADDED (`playerCount`) update the named built-in counters when those integer parameters are supplied. Custom names and explicit state actions remain available.

State transitions are evaluated serially in event ingress order and committed before external actions are dispatched. Later rules in the saved list can therefore test counter/flag changes made by earlier rules for the same event. External hardware actions retain priority over slower audio/media work. Use separate emitted events when an explicit later phase is required. Inspect current values with authenticated `GET /api/rules/runtime-state` while testing.

### Grouped triggers and event chains

ALL trigger items must have occurred within the group's Window ms; ANY needs one matching item. Group results are combined using the outer ALL/ANY setting. A successful match consumes its accumulated inputs, so one old switch hit cannot repeatedly qualify a multi-input rule. The default group window is 750 ms. Button hold/repeat/double-click parameters and switch active/inactive duration parameters filter their corresponding generated events.

An Emit Event action can trigger another rule. Connected events return through the ESP confirmation path; offline simulation evaluates the chain locally. Generated chains stop after 16 levels to bound accidental cycles. Duplicate confirmed event identities do not increment state twice; deduplication/history storage is bounded.

### Hardware safety and testing

Pi-approved output/pulse actions use the ESP's existing output executor, arming requirement, cooldown, maximum-on/hold limits and recovery handling. A Pi hardware decision expires after 250 ms; it cannot replay an old press after recovery or energize an input-held output after release. Host loss or a slow Pi can therefore suppress a conditional hardware action. Keep latency-critical flipper/bumper response in a separate unconditional ESP rule and put scoring/counters/media in a Pi rule.

Switch closed/open/changed and active/inactive duration events are generated on the ESP. NFC matching conditions on an incoming NFC_MATCHED event filter its `tagId` (or `uid`) against the configured IDs; an actual NFC reader still requires a driver that publishes those events. This change does not add a reader driver or infer hardware wiring.

Delay and LED Pattern remain explicitly planned registry entries, hidden from the normal action picker; they are not executable actions. Supported audio/media/lighting actions still depend on valid configured assets, scenes and devices.

Validate with coils disabled first: increment a counter on repeated input, check its threshold, verify a flag blocks the reward, test ALL/ANY timing and confirm a single reward event reaches scoring/audio/media. Then test on the target Pi/ESP, including lost connection, release while the Pi is busy, re-sync, reboot and re-arming. Host tests and a successful firmware build do not replace physical timing and safety verification.
